# 00 — General Plan: Game Integration API

> Source: *KenTech — Backend Go Developer Technical Assessment v2.0 (27 Oct 2026)*.
> This is the master plan. Each phase below gets its own detailed plan file
> (`docs/plans/NN-<name>.md`) written **before** implementation starts.

---

## 1. Goal

Build a Go backend that lets third-party casino games place (Withdraw), settle
(Deposit) and revert (Cancel) bets for players, while keeping our own records
consistent with an **intentionally unreliable** Wallet service.

What the reviewers value most (section 12 of the assessment), in order of risk:

1. Failure handling and consistency when the Wallet fails or its outcome is unknown.
2. Idempotency and concurrency (retries, simultaneous duplicates).
3. Money handling (exact arithmetic, types, validation).
4. Cancel semantics (every case of section 8.5).
5. Architecture/code quality, security, operability, and the reasoning in `DESIGN.md`.

> **Guiding principle:** a smaller solution that handles failures well beats a
> larger one that only handles the happy path. Nice-to-haves come last.

## 2. Key technical decisions (initial — confirm/refine in each phase plan)

| Topic | Decision | Why |
|---|---|---|
| Language | Latest stable Go (single module at repo root) | Required. Monorepo = one `go.mod`. |
| HTTP | `net/http` standard library (Go ≥ 1.22 method/path routing) | No framework needed; fewer deps to explain. |
| Database | PostgreSQL 16 | Transactions, `UNIQUE` constraints, `NUMERIC`, row/advisory locks. |
| DB access | `jackc/pgx/v5` (+ `pgxpool`), plain parameterised SQL | Explicit SQL is easier to defend in the interview. `sqlc` optional later. |
| Migrations | `pressly/goose` (SQL files, embedded with `embed`) | Runs at startup and from CLI; seed is a migration. |
| Money | `shopspring/decimal` wrapped in a domain `Money` type; DB `NUMERIC(20,2)` | Never `float64`. Closest analogue to .NET `decimal`. |
| JSON money | Custom `MarshalJSON`/`UnmarshalJSON` (number, max 2 decimals) via `json.Number` | Avoid float round-trip when decoding. |
| IDs | Wallet user ID / betId: `int64` (`BIGINT`); transactionId: UUID string | IDs exceed 32-bit; betId must be integer generated by us. |
| Auth | JWT HS256 (`golang-jwt/jwt/v5`), bcrypt (`golang.org/x/crypto/bcrypt`) | Subject = wallet user ID; secret + TTL from env. |
| Logging | `log/slog` (JSON handler) | Structured logs, stdlib. Never log tokens/passwords/API key. |
| Config | Environment variables + `.env.example` | Required. |
| Tests | stdlib `testing` (+ `testify` if useful), fake Wallet, table-driven tests | Deterministic failure simulation is required. |
| Containers | Multi-stage `Dockerfile` + `docker-compose.yml` (api + postgres + wallet) | Single `docker compose up`. |

## 3. Core reliability design (the heart of the assessment)

This is the initial direction; **Phase 1 (Wallet spike) may change it**.

1. **Intent first (write-ahead record).** Before calling the Wallet, persist the
   transaction as `PENDING` in its own committed DB transaction, including the
   payload hash, the reserved `betId` and the `reference` we will send. If the
   process dies after this point, the record survives → *no lost Wallet calls*.
2. **Idempotency by unique key.** `UNIQUE(provider_transaction_id)` for
   WITHDRAW/DEPOSIT; `UNIQUE(cancelled_transaction_id)` for CANCEL. Same key +
   same payload hash → replay (200, no Wallet call). Different hash → 409.
   Two concurrent identical requests: only one insert wins; the other reads the
   winner's record.
3. **Per-player serialisation.** Operations of the same player are serialised
   (PostgreSQL advisory lock keyed by wallet user ID, or `SELECT … FOR UPDATE`
   on the player row). This keeps `oldBalance` and bet state coherent.
4. **Outcome classification of each Wallet call.**
   - 2xx → `COMPLETED` (update bet in the same DB transaction).
   - Definitive "not applied" (e.g. insufficient funds, validation 400) →
     `FAILED` (+ 422 / 502).
   - Timeout, connection reset, 5xx or anything ambiguous → stays `PENDING` → 202.
5. **Bounded waiting.** Every Wallet call uses `context.WithTimeout`; retries (if any)
   are few, with backoff, and only when safe.
6. **Resolution of PENDING.** At least one mechanism: (a) resolve when the provider
   retries, and/or (b) a background reconciler. The exact mechanism depends on what
   the spike reveals (e.g. whether the Wallet de-duplicates by `reference`/`betId`).
7. **Observability.** One structured log line per Wallet call with
   `transactionId`, `providerTransactionId`, `betId`, operation, duration, outcome.

## 6. Working agreement (applies to every phase)

- **Plan before code.** Each phase starts by writing `docs/plans/NN-*.md` using
  the template below; implementation starts only after it is approved.
- **Small commits.** One logical change per commit, each one compiling and with
  tests green (`go build ./... && go test ./...`). Conventional Commits:
  `feat(withdraw): …`, `test(domain): …`, `docs(design): …`, `chore(docker): …`.
- **Docs travel with code.** If a phase changes behaviour, the same phase updates
  `README.md` / `DESIGN.md` / `ARCHITECTURE.md`.
- **Decisions are recorded.** Any ambiguity resolved → a line in `DESIGN.md`.

### Template for specific plans

```markdown
# NN — <Phase name>

## Goal
## Requirements covered (assessment sections)
## Design decisions (and alternatives rejected)
## Files to create / modify
## Commit sequence
1. `type(scope): message` — what it contains, how it is verified
2. …
## Test plan (unit / integration / manual curl)
## Open questions
## Definition of done
```

## 7. Open questions to resolve early

1. ~~Wallet behaviour (Phase 01): does it de-duplicate by `reference` or `betId`?
   Does it expose any way to query a past transaction? What do "error after
   applying" responses look like? Decimal format of amounts in requests/responses?~~
   **Resolved in Phase 01** → [`docs/wallet-findings.md`](../wallet-findings.md):
   withdraws are de-duplicated by (`betId`, `reference`) and deposits by
   `reference`, in memory only; there is no transaction lookup; "error after
   applying" is a `500 {"code":"666"}` (and sometimes a dropped connection);
   balances come back as JSON strings with exact decimals.
2. ~~Zero-amount deposit: forward to the Wallet or not?~~ **Resolved in
   Phase 09:** not forwarded (no money moves); the balance is still read for
   `oldBalance` → `DESIGN.md` §4.
3. Retry after `FAILED`: return the stored failure (pure idempotency) or allow a
   new attempt? (Decide in Phase 11; the assessment asks to document it.)
   *Interim since Phase 08:* `409 CONFLICT` "previous attempt failed", no Wallet call.
4. While a request is `PENDING` and the same key arrives again: re-try the
   resolution, or just return 202? (Phase 11.)
5. ~~Usernames/passwords for the 4 seeded players (Phase 04).~~ **Resolved in
   Phase 04:** `player_usd`, `player_eur`, `player_kes`, `player_usd_2`, each
   with its own password, documented in `README.md`.
6. Where do errors live? Today every business error is in `Domain/errors.go`.
   Alternative raised in Phase 06: *each error is declared in the lowest layer
   that produces it* (e.g. `ErrMissingCredentials`, `ErrIdempotencyConflict`
   in `Actions/errors.go`), always wrapping one of the seven `Domain`
   categories, so the HTTP mapping does not change. Errors that are part of a
   port's contract (`ErrInvalidCredentials`, `ErrInvalidToken`, the §8.5 cancel
   errors) stay in `Domain` either way. Rejected: a 1:1 copy of every domain
   error in `Actions`. **Revisit once Withdraw, Deposit and Cancel exist
   (after Phase 10).**
