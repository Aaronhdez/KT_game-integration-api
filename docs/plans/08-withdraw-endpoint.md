# 08 — Withdraw endpoint

## Goal

Let a game place a bet for the authenticated player: `POST /api/v1/withdraw`
takes the stake from the Wallet, and our records stay consistent with it even
when the Wallet fails or its outcome is unknown. At the end of the phase:

- the first **state-changing** use case exists, `actions.WithdrawCommandHandler`,
  and it follows the reliability design end to end: per-player lock →
  idempotency lookup → `oldBalance` read → `PENDING` committed **before** the
  Wallet call → classify the Wallet result → `COMPLETED` / `FAILED` / stays
  `PENDING`;
- a completed withdraw creates the bet (`PLACED`) with the `betId` reserved
  before the Wallet call;
- a retried request with the same `providerTransactionId` never reaches the
  Wallet twice: same payload → replay, different payload → `409`, two
  simultaneous identical requests → one Wallet call;
- provider transaction IDs are unique **across the whole system** (§6.1), not
  per player as Phase 04 built them (one migration fixes it);
- status codes `201` (new, completed), `200` (replay), `202` (outcome unknown,
  `PENDING`), `400`, `401`, `409`, `422`, `502` — **never `504`**, which §7.3
  reserves for reads;
- the persistence ports get their first consumer: `Startup` wires
  `persistence.PlayerLocker` and a real UUID generator (`Shared/id`);
- `Domain/domaintest` gets the in-memory repositories, locker and ID generator
  deferred by Phase 04.

No new dependency and no new configuration. Resolving a `PENDING` withdraw is
Phase 11.

## Requirements covered (assessment sections)

- **8.3** — request `{currency, amount, providerTransactionId}`; amount `> 0`;
  currency = player's wallet currency; `betId` generated by us; a completed
  withdraw creates a `PLACED` bet; insufficient funds → `422`, `FAILED` record
  kept, no bet.
- **6.1** — provider transaction IDs of `WITHDRAW`/`DEPOSIT` unique across the
  whole system; a player only acts on their own transactions.
- **7.1** — idempotency by `providerTransactionId`: replay vs `409 CONFLICT`.
- **7.2** — `201` / `200` (stored result, current state) / `202`.
- **7.3** — error body and codes; `502` only when we established that nothing
  was applied; `504` not used by operations.
- **7.4** — response fields `transactionId`, `providerTransactionId`,
  `oldBalance`, `newBalance` (`null` while `PENDING`), `status`, `betStatus`
  (`null` while the withdraw is `PENDING`).
- **9.1** — no lost Wallet calls: `PENDING` committed before the call.
- **9.2** — no duplicate effects, including concurrent duplicates.
- **9.3** — not applied → error + `FAILED`; unknown → `PENDING` + `202`.
- **9.5** — bounded waiting: one balance read (client: ≤ 2 attempts) + one
  operation call (6 s), under the server's 30 s `WriteTimeout`.
- **9.6** — operations of one player serialised (`PlayerLocker`, Phase 04).
- **9.7** — one log line per withdraw with `transactionId`,
  `providerTransactionId`, `betId`, outcome and duration (the client already
  logs each Wallet call).

## Design decisions (and alternatives rejected)

| Decision | Why | Rejected alternative |
|---|---|---|
| **Request** exactly as §8.3: `{"currency", "amount", "providerTransactionId"}`; the player only from the token. `amount` decoded into `*domain.Money` so a missing field is a `400`, not a zero | A pointer tells "absent" from "0" (same problem recorded in `DESIGN.md` for deposits). | Taking `userId` from the body: a player could act for another one. |
| **Response** exactly the six fields of §7.4, in the order of the §8.3 example: `transactionId`, `providerTransactionId`, `oldBalance`, `newBalance`, `status`, `betStatus` | The assessment defines the shape; `betId`, `amount`, `currency` stay internal (logged, stored). Amounts via `Money.MarshalJSON` (two decimals, never `float64`). | Adding extra fields "for convenience". |
| **Validation before the lock and before any Wallet call**: provider ID (`ParseProviderTransactionID`), amount `> 0` (`NewWithdraw`), currency (`ParseCurrency`), currency = player's currency (`ErrCurrencyMismatch`, `400`) | §7.3 lists all of them as `400`. The Wallet validates almost nothing (findings Q4); a request we have not validated is never sent. No lock held for a bad request. | Letting the Wallet answer `InvalidCurrency` (a `502` and a `FAILED` row for a client mistake). |
| **Provider transaction ID unique across the system**: migration `00005` replaces the per-player index with `UNIQUE (provider_transaction_id) WHERE type IN ('WITHDRAW','DEPOSIT')`, **same index name** (`transactions_idempotency_key`), so `mapUniqueViolation` does not change. An ID already used by **another** player → `409 CONFLICT` with a generic message | §6.1 says so explicitly; Phase 04 scoped it per player to avoid revealing other players' data. A `409` with a generic message reveals only that the ID is taken — which §6.1 makes unavoidable — never whose it is or its content. Lookups stay scoped by player, so another player's transaction is never returned. | Keeping the per-player index (contradicts §6.1); a global lookup that returns the other player's transaction (would leak it). |
| **Order inside the lock**: (1) idempotency lookup → (2) Wallet `Balance` → (3) reserve `betId`, insert `PENDING` (committed) → (4) Wallet `Withdraw` → (5) store the outcome in one DB transaction | Replays never touch the Wallet. `oldBalance` "as observed by your service" (§7.4) is read under the lock, so no other operation of the player moves it before our call (general plan §3.3). Intent-first (§9.1). | Balance read before the lock (another withdraw of the same player could slip in between). |
| **`oldBalance` from a Wallet balance read.** If the read fails **or times out** → `502 WALLET_ERROR` and **nothing is stored** | §5.3: the old balance is our responsibility. §7.3: `504` is only for reads, and here no withdraw was sent, so we *established* it was not applied → `502`. Nothing is stored because there is no Wallet call to keep track of (§9.1); the provider can simply retry with the same ID. Phase 03 already fixed "a failed `oldBalance` read → the operation is not started". | Recording a `FAILED` row: it would burn the provider ID for a transient read error (a retry would get `409` forever), and `old_balance` would be unknown. `504`: forbidden for operations by §7.3. |
| **Idempotency = compare the stored fields**, no payload hash: same provider ID **and** same `amount` and `currency` → replay; otherwise `ErrIdempotencyConflict` (`409`) | The §8.3 request has exactly three fields and all are columns of the transaction, so the comparison is exact, readable and needs no hash column. | A SHA-256 of the canonical body in a new column: opaque and sensitive to JSON formatting. |
| **Replay rules** (no Wallet call in any of them): `COMPLETED` (or later `CANCELLED`) → `200` with the stored transaction and the bet's **current** status; `PENDING` → `202` with the stored transaction; `FAILED` → `409 CONFLICT` "a previous attempt with this provider transaction id failed" | §7.2: a replay returns the stored result reflecting the current state; `202` whenever it is `PENDING`. For `FAILED`, repeating the original `422`/`502` would need the failure reason, which no column stores. Final `FAILED` policy: general-plan open question 3 (Phase 11), recorded in `DESIGN.md` §3. | Re-sending a `PENDING` to the Wallet now: that is Phase 11's resolution, with its own timing rules (findings Q8). A `failure_code` column. |
| **Outcome classification** (from the port contract): `nil` → `COMPLETED` + bet `PLACED` (`201`); `ErrWalletAppliedBalanceUnknown` → `COMPLETED` with `newBalance = oldBalance − amount` (`201`); `ErrInsufficientFunds` → `FAILED`, `422`; `ErrWalletRejected` → `FAILED`, `502` (logged at `error`); **anything else** → stays `PENDING`, `202` | Only a definitive "not applied" may become `FAILED` (§9.3, AGENTS.md). The derived `newBalance` is exact because the balance was read under the lock just before the call; the case is rare (a `2xx` with an unusable body). | Leaving `newBalance` `null` on a `COMPLETED` (§7.4 reserves `null` for `PENDING`); a second balance read (up to 20 s more inside the request). |
| **After the Wallet call, DB writes use `context.WithoutCancel(ctx)`** (bounded by their own short timeout) | If the provider disconnects while we wait, the request's `ctx` is cancelled — but the Wallet may have applied the withdraw, and we must still record it. | Using the request `ctx` (a disconnect would leave an applied withdraw recorded as `PENDING` for no reason). |
| **Storing the outcome fails** (DB down after the Wallet answered) → log at `error`, answer `202` with the transaction as stored (`PENDING`) | The database still says `PENDING`; answering `201` would describe a state we could not save. Phase 11 resolves it (re-send → `409` → `COMPLETED`). | `500 INTERNAL_ERROR`. |
| `ErrTransactionExists` on insert → look up the player's own transaction again: found → replay rules; not found → the ID belongs to another player → `409` | For the same player it cannot happen while the advisory lock works (the index is the safety net, §9.2). For two players the lock does not serialise them, so the global index is the real guard. | Returning `409` always (wrong for an identical duplicate of the same player). |
| **Result type** `actions.TransactionResult{Transaction, BetStatus *domain.BetStatus, Replayed bool}`; the controller picks the status: `PENDING` → `202`, `Replayed` → `200`, else `201` | The use case states facts, `Application` owns HTTP. Deposit and Cancel (Phases 09–10) return the same §7.4 shape. | The use case returning an HTTP status. |
| **Transaction IDs: `Shared/id.UUID`**, version 4 from `crypto/rand`, ~15 lines, stdlib only | Few dependencies (general plan); a v4 UUID is 16 random bytes with two fields set — easy to explain live. The column type `UUID` validates it. | `github.com/google/uuid` (a dependency for 15 lines). |
| **Fakes in `domaintest`**: one `FakeStore` holding transactions and bets, which implements `PlayerLocker` (a mutex per player) and `UnitOfWork` (`Atomic` works on a copy and keeps it only if `fn` returns `nil`), enforces the same unique rules as PostgreSQL (global provider ID), and has error hooks; `FakeIDGenerator` (sequential UUID-shaped IDs) | Phase 04 deferred them to their first consumer. Rollback semantics matter (a failed outcome write must leave `PENDING`). One store keeps the two repositories consistent like one database. | Mocks per method (brittle, test the calls instead of the behaviour). |
| **Logging in the use case**: one line per withdraw (`transaction_id`, `provider_transaction_id`, `user_id`, `bet_id`, `amount`, `outcome`, `replayed`, `duration_ms`); `info` completed/replay, `warn` pending/insufficient funds, `error` rejected or outcome not stored | §9.7: the client logs each Wallet call but does not know the provider ID. | Logging only in the controller (it does not know the outcome detail). |
| **Time budget accepted**: worst case ≈ 20.2 s (balance read + its retry) + 6 s (operation) + DB ≈ 27 s, under the 30 s `WriteTimeout` | Documented in `DESIGN.md` §1 (timeouts row). | A client option to skip the balance retry (more code for a rare case). |
| The controller depends on the concrete `*actions.WithdrawCommandHandler`, wrapped in `RequireAuth` by `Startup` | Same pattern as Phases 06–07. | An interface for one implementation. |

### Flow

```
POST /api/v1/withdraw  (RequireAuth → user ID)
  decode {currency, amount, providerTransactionId}           bad JSON / missing amount → 400
  WithdrawCommandHandler.Execute
    validate provider ID, amount > 0, currency               → 400
    players.FindByID → currency == player currency           → 404 / 400
    WithPlayerLock(user):
      Atomic: FindByProviderTransactionID (own player)
        found, same amount+currency → replay  (200 / 202 / 409 if FAILED)
        found, different            → 409 CONFLICT
      wallet.Balance                                          → 502 (failure or timeout), nothing stored
      Atomic: bets.NextID, NewWithdraw(PENDING), Insert        ← committed (intent-first)
        ErrTransactionExists → own lookup again: replay, or 409 (another player's ID)
      wallet.Withdraw(reference = transaction ID, betId)
      Atomic (ctx WithoutCancel):
        applied      → tx.Complete, bets.Insert(PLACED), Update  → 201
        insufficient → tx.Fail, Update                           → 422
        rejected     → tx.Fail, Update                           → 502
        unknown      → nothing to write                          → 202
```

  concurrent duplicates and another player's ID; controller and router.

  ```bash
  TOKEN=$(curl -s -X POST localhost:8080/api/v1/auth/login \
       -H 'Content-Type: application/json' \
       -d '{"username":"player_usd","password":"…"}' | jq -r .token)
  BODY='{"currency":"USD","amount":10.50,"providerTransactionId":"prov-tx-0001"}'
  curl -i -X POST localhost:8080/api/v1/withdraw -H "Authorization: Bearer $TOKEN" -d "$BODY"   # 201 or 202
  curl -i -X POST localhost:8080/api/v1/withdraw -H "Authorization: Bearer $TOKEN" -d "$BODY"   # 200 (or 202 again)
  # same id, amount 11.00 → 409; currency EUR → 400; amount 999999 → 422
  # same id with player_usd_2's token → 409
  # repeat with new ids ~10 times: expect some 202 (≈ 27 % per findings Q6)
  psql … -c "SELECT status, count(*) FROM transactions GROUP BY status"
  ```
  Check: every `201`/`200` has a `PLACED` bet; every `202` is `PENDING` with no
  bet; logs have one use-case line per request, no token or API key.
